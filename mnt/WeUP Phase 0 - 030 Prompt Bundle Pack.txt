P01 — Establish WeUP World Surface Runtime
You are working inside the WeUP_Phase0_AIStudio repository.


Goal:

Context:
The app currently behaves like a single large client-side orchestration surface. I want to preserve the WeUP design doctrine:
- persistent map-first world surface
- no-scroll single viewport
- layered overlays instead of page navigation
- cinematic transitions
- modal depth model
- mobile-first interaction model


What to do:
1. Inspect the existing frontend structure and identify runtime responsibilities currently mixed together:
   - view composition
   - UI state
   - map state
   - modal state
   - async event feed loading
   - temporal filtering
   - saved/profile/social/add-event interaction flows
2. Refactor the app into a clearer runtime architecture with these logical layers:
   - app shell / world surface
   - feature state orchestration
   - data access services
   - domain models
   - UI components
   - shared hooks / utilities
3. Introduce a scalable folder structure appropriate for a Next.js Phase 0 MVP, such as:
   - app/
   - features/
   - domains/
   - services/
   - hooks/
   - lib/
   - components/
   - styles/
4. Create an explicit world-surface coordinator layer that owns:
   - active mode
   - modal stack
   - selected event
   - map interaction state
   - temporal state
   - side-panel state
5. Preserve visual behavior unless technically necessary to adjust.
6. Remove ad hoc coupling between presentational components and orchestration logic where possible.
7. Keep the frontend in TypeScript and make types strict.
8. Do not add fake backend logic. Only prepare clean seams for real APIs.


Deliverables:
- revised folder structure
- refactored coordinator/runtime files
- extraction of orchestration logic from page.tsx
- brief architecture note in markdown explaining the runtime spine
- list of old responsibilities and where each moved


Constraints:
- do not break the current UX flow
- do not introduce Redux unless clearly justified; prefer React context + custom hooks or a lightweight local architecture
- preserve map-first rendering model
- avoid overengineering


Acceptance criteria:
- app/page.tsx becomes thin and mostly composition-oriented
- runtime responsibilities are separated cleanly
- feature seams are obvious for future backend integration
- TypeScript passes
- the app still renders the world surface correctly


Output format:
1. Explain the target runtime architecture
2. Show the proposed folder structure
3. Generate the code changes
4. Summarize migration decisions and tradeoffs
