0. Abstract
0.1 Product Intent
WeUP Phase 0 is a map-first nightlife radar system, not a traditional app.
It is designed to:
* Surface real-time cultural activity
* Convert flyers → structured events → spatial signals
* Allow users to scan a city as a living system
Core loop:
Upload → Extract → Parse → Place → Discover → Save


________________


0.2 Phase 0 Functional Scope
The MVP includes:
* Map Surface (Primary Interface)
* Flyer Upload Pipeline
* OCR + Event Parsing
* Calendar Exploration Layer
* Event Detail Modal
* Save / Shortlist System
All features must operate within:
A single viewport, layered interaction system
________________


0.3 Non-Goals (Phase 0)
Explicit exclusions to avoid system bloat:
* Native ticketing infrastructure
* Complex social networking
* Messaging systems
* Deep recommendation engines
* Full promoter dashboards
These are deferred to Phase 1+.
________________


0.4 Core UX Principle
The system is not a collection of screens.
It is a spatial operating layer over a city.
Users do not “navigate pages.”
They move through states of focus.
________________


0.5 Experience Target
The interface should feel like:
* A live cultural radar
* A nightlife command surface
* A signal scanner for real-world activity
It should not feel like:
* A CRUD dashboard
* A ticketing website
* A social feed
* A generic mobile app
________________


0.6 Success Criteria (Phase 0)
A successful Phase 0 delivers:
* Immediate understanding (≤ 5 seconds)
* Clear mode awareness at all times
* Zero viewport overflow
* Smooth upload → discover loop
* High visual clarity under density
________________


1. Design Philosophy
1.1 Map as Primary Surface
The map is:
* The default state
* The main interaction layer
* The source of truth for discovery
All other features must:
* Attach to the map
* Emerge from the map
* Return to the map
________________


1.2 Single-Viewport Doctrine
Strict rule:
The entire application must fit within one viewport at all times.
Implications:
* No page-level scrolling
* Only contained scrolling inside modal regions (if necessary)
* All transitions occur via:
   * overlays
   * modals
   * state changes
________________


1.3 One Active Mode Rule
At any moment:
Only one mode may dominate user attention.
Examples:
Mode
	Dominant Surface
	Map
	Map
	Calendar
	Calendar
	Event Detail
	Event modal
	Upload
	Upload flow
	Violation of this rule causes:
* cognitive overload
* visual crowding
* interaction ambiguity
________________


1.4 Layered OS Model (Not Screen-Based)
WeUP behaves like an operating system:
* Layers stack intentionally
* Depth communicates priority
* Background recedes when focus increases
Not:
* page → page navigation
* tabbed app switching
________________


1.5 Signal Over Noise
Every element must justify its presence.
Remove:
* redundant controls
* persistent elements without context
* duplicated filters
Prioritize:
* clarity
* focus
* immediate comprehension
________________


1.6 Cinematic Minimalism
Visual identity:
* Deep black base
* Neon green signal accents
* Glass + blur materials
* Strong typography
But:
Minimalism is enforced through control reduction, not visual stripping.
________________


1.7 Contextual UI (Adaptive Visibility)
UI elements must appear only when relevant.
Examples:
* Time slider → only in Map Mode
* Bottom nav → suppressed in deep modal states
* Filters → contextual, not global
________________


1.8 Spatial Breathing Room
The interface must:
* Avoid vertical compression
* Avoid stacking bars (nav + slider + cards)
* Preserve negative space
Result:
The user feels they are scanning a city, not reading a screen.
________________


1.9 Deterministic Interaction
Every interaction must be:
* predictable
* reversible
* visually explained
No hidden states.
No ambiguous gestures.
________________

3. Spatial & Layout Principles
3.1 Viewport Budgeting
The viewport is a finite resource.
You must explicitly allocate vertical space:
Zone
	Max Height
	Purpose
	Top HUD
	8–12%
	Branding + status
	Map Canvas
	70–80%
	Primary interaction
	Bottom Zone
	12–18%
	Navigation OR contextual control
	Rule:
Only one bottom element may occupy the bottom zone at a time.
This directly fixes:
* time slider vs nav collision
* stacked bottom UI clutter
________________


3.2 Safe Zones (Thumb + System)
Design for one-handed operation:
* Bottom 25% = primary interaction zone
* Avoid placing conflicting controls in the same thumb arc
* Floating elements must not overlap gesture zones
Constraint:
* Upload button must not block:
   * nav taps
   * slider interaction
   * modal expansion gestures
________________


3.3 Edge Anchoring vs Floating Controls
Edge Anchored (Preferred)
* Bottom navigation
* Time access trigger
* Close/back controls
Floating (Restricted)
* Only for:
   * contextual quick actions
   * temporary states
Rule:
Floating controls must disappear when focus increases.
________________


3.4 Density Tiers
Define UI density explicitly:
________________


Tier 0 — Ambient (Map Mode)
* Minimal UI
* Maximum breathing room
* Signals over controls
________________


Tier 1 — Informational (Calendar / Saved)
* Moderate density
* Structured grid
* Controlled scroll region
________________


Tier 2 — Focus (Event Detail / Upload)
* High information density
* Fully intentional layout
* No background competition
________________


Rule:
Density must increase only when focus increases.
________________


3.5 Negative Space as Signal Amplifier
Negative space is not empty—it is functional clarity.
Remove:
* redundant bars
* stacked overlays
* unnecessary labels
Preserve:
* spacing between cards
* margin around modals
* map visibility
________________


3.6 Vertical Conflict Elimination
The current MVP problem:
[Top Bar]
[Map]
[Event Card]
[Time Slider]
[Bottom Nav]


This is invalid.
Correct model:
Map Mode:
[Top HUD]
[Map Canvas]
[Bottom Nav]


Time Active (Expanded):
[Top HUD]
[Map Canvas]
[Time Tray replaces Bottom Nav]


________________


3.7 Modal Containment
All modal systems must:
* Stay within viewport
* Not overflow edges
* Use internal scroll if needed
Rule:
The page never scrolls. Only modal content can scroll internally.
________________


3.8 Spatial Priority Rule
At any moment:
1. One dominant surface
2. One supporting control layer
3. Everything else recedes
________________

Close

6. Map Mode (Primary Surface)
6.1 Purpose
Map Mode is the default operational state of WeUP.
It is where the user:
* scans the city
* reads cultural density
* filters by time
* opens event signals
* decides where to go next
This is not a dashboard.
This is a live spatial discovery surface.
________________


6.2 Experience Goal
Map Mode should feel like:
* nightlife radar
* cultural heat scanner
* city signal field
* real-time urban interface
It should not feel like:
* event list over a map
* rideshare map clone
* cluttered GIS screen
* admin monitoring tool
________________


6.3 Dominant Surface Rule
In Map Mode:
The map must occupy the overwhelming majority of perceptual attention.
This means:
* no large persistent cards
* no globally expanded drawers
* no constant modal stack
* no permanent time bar
* no visual obstruction of the city surface
________________


6.4 Layout Structure
Top HUD
Contains only:
* WeUP wordmark / compact identity
* optional city label
* small status pill such as:
   * Live
   * Tonight
   * Active Signals
This region must remain compact.
________________


Main Canvas
Contains:
* dark city map
* event signals
* cluster glows
* optional subtle district overlays
* optional live pulse effects
This is the hero zone.
________________


Bottom Zone
Contains:
* bottom nav in default state
* OR time tray when time is expanded
* never both fully active at the same time
________________


6.5 Signal Visualization System
Event representation must be layered by importance.
Signal Types
Micro Signals
* small neon dots or tiny glow points
* used for lower-confidence or lower-priority events
Standard Signals
* medium glowing pins
* default event marker
Featured Signals
* brighter ringed pins
* boosted or important events
Cluster Signals
* grouped pulse nodes
* show event count and intensity
________________


6.6 Visual Behavior of Signals
Signals should:
* glow subtly at rest
* brighten on proximity or tap
* pulse lightly when active in selected time range
They should not:
* bounce excessively
* obscure map readability
* use too many competing colors
________________


6.7 Event Preview Pattern
Map Mode should not display full event cards by default.
Instead use:
Peek Card Pattern
When a signal is tapped:
* a compact preview card rises from the lower portion of the map
* shows:
   * title
   * venue
   * time
   * one category tag
* includes:
   * open detail
   * quick save
The peek card must remain compact.
________________


6.8 Peek Card Rules
Peek card may:
* occupy only a small percentage of vertical space
* collapse easily
* disappear if another signal is selected
Peek card may not:
* become a giant permanent drawer
* compete with the map as a primary layer
________________


6.9 Time System in Map Mode
Map Mode is the primary home of time.
Recommended implementation
* compact time pill in lower right or lower center
* tap expands into time tray
* tray temporarily replaces nav prominence
The time system must feel like a city-layer switcher.
________________


6.10 Filters in Map Mode
Filters must remain minimal.
Recommended:
* genre filter chip
* neighborhood filter chip
* maybe one “live now” toggle
Do not expose full filter complexity by default.
Advanced filtering should be expandable, not persistent.
________________


6.11 Motion in Map Mode
Transitions should be subtle:
* map remains stable
* selected signal slightly enlarges
* preview card lifts softly
* time shift animates signal fade/repopulation
The map should feel alive, not chaotic.
________________


6.12 Empty / Sparse States
If few events exist:
* show softer, more spacious map
* include prompt:
   * “No major signals in this time layer”
   * “Try Tonight” or “Expand area”
Sparse state must still feel premium.
________________


6.13 Performance Rule
Map Mode must remain fast under density.
Requirements:
* clustering at scale
* viewport query bounding
* lazy-loading detail metadata
* reduced effect density when many signals exist
________________

7.7 Calendar Content Model

7.9 Card Information Hierarchy
Each calendar card should include:

* event title
* time
* venue or neighborhood
* small category tag
Optional
* flyer thumbnail
* signal intensity
* featured badge

   * inline editing (not separate forms)

   * full-page form transitions
   * multi-screen editing

   * how event appears on map or calendar

   * publish event
   * optionally boost (future monetization hook)
Post-save:
   * event enters system
   * visible on map/calendar

9.10 Error Handling

   * show partial extraction
   * allow full manual entry fallback
   * never block submission entirely
________________


9.11 Upload Exit Paths

   * go to event detail
   * return to map
   * optionally prompt:
   * “Boost visibility?”
________________


9.12 Motion Behavior

   * step slides or fades
   * progress indicator updates
   * no abrupt context switches

9.13 System Integrity Rule
The upload flow must always feel faster than manual entry.

12. Component System
12.1 Purpose
The component system exists to ensure:
   * consistency
   * speed of implementation
   * predictable behavior
   * reusable interaction patterns
Every component in WeUP must serve one of three roles:
   1. Navigation
   2. Discovery
   3. Focus / Input
No component should exist without a defined role in the state system.
________________


12.2 Component Categories
The WeUP component library should be organized into the following groups:
A. Shell Components
High-level layout and navigation surfaces.
   * AppShell
   * TopHUD
   * BottomNav
   * ModeContainer
   * ModalLayer
   * BackdropLayer
________________


B. Discovery Components
Map, calendar, event signal, and browse components.
   * MapCanvas
   * SignalPin
   * SignalCluster
   * EventPeekCard
   * CalendarBoard
   * CalendarCard
   * FeaturedEventTile
   * FilterChip
   * TimePill
   * TimeTray
________________


C. Focus Components
High-attention components used in modal and detail states.
   * EventDetailModal
   * EventHero
   * MetadataBlock
   * CTACluster
   * UploadWizard
   * OCRStatusPanel
   * ParsedField
   * InlineEditField
   * SaveConfirmationDialog
________________


D. Identity Components
User and personal collection surfaces.
   * SavedGrid
   * SavedCard
   * EmptyStatePanel
   * ProfileHeader
   * PreferenceGroup
   * ActivityList
________________


E. Feedback Components
Status and supporting system communication.
   * LoadingState
   * Toast
   * InlineError
   * FieldConfidenceHint
   * ProgressStepper
   * ConfirmationSheet
________________


12.3 Shell Component Contracts
AppShell
Owns:
   * viewport sizing
   * safe-area padding
   * root layering
   * mode switching container
Rules:
   * no page scroll
   * full-height containment
   * all modes render inside shell
________________


TopHUD
Contains:
   * WeUP identity
   * local mode label
   * compact status indicators
Rules:
   * always compact
   * never becomes a full toolbar
   * should adapt by mode
________________


BottomNav
Contains:
   * Map
   * Calendar
   * Upload
   * Saved
   * Profile
Rules:
   * max 5 destinations
   * active icon state required
   * can suppress in focus-heavy modes
   * center upload affordance allowed, but not oversized
________________


ModalLayer
Responsible for:
   * calendar takeover
   * event detail chamber
   * upload flow
   * system dialogs
Rules:
   * centralized layering contract
   * no ad hoc modal stacking
________________


12.4 Discovery Component Contracts
MapCanvas
Owns:
   * map rendering
   * signal placement
   * viewport interactions
   * spatial background continuity
Rules:
   * always fast
   * never blocked by unnecessary overlays

   * time relevance
   * save status
Rules:
   * minimal idle motion

________________


SignalCluster
Represents grouped events.

   * count
   * intensity
   * optional glow scaling
Rules:
   * count readable
   * tap expands cluster region or zooms intelligently
________________


EventPeekCard

   * quick insight without leaving map mode
Contains:
   * title
   * venue
   * time
   * one tag
   * save shortcut
   * open detail action
Rules:
   * compact only
   * must not become a giant sheet
   * easy dismissal
________________


CalendarBoard
Owns:
   * date grouping
   * masonry tile composition
   * internal scroll region
   * local calendar controls
Rules:
   * must behave as a destination surface
   * no generic list rendering
________________


CalendarCard / FeaturedEventTile
Support variants:
   * compact
   * standard
   * featured
Rules:
   * consistent metadata hierarchy
   * image optional, not required

FilterChip

14. Motion System
14.1 Purpose
Motion in WeUP is not decorative.
It exists to communicate:
   * mode change
   * layer transition
   * focus shift
   * system response
   * spatial continuity
________________


14.2 Motion Philosophy
Motion should feel:
   * cinematic
   * composed
   * premium
   * directional
   * urban
   * fluid
It should not feel:
   * bouncy
   * playful
   * chaotic
   * game-like
   * over-animated
________________


14.3 Core Motion Roles
Motion must serve one of the following:
   1. Reveal
   2. Transition
   3. Confirm
   4. Recede
   5. Guide
________________


14.4 Reveal Motion
Used for:
   * event peek card appearing
   * modal entering
   * time tray opening
   * toasts appearing
Behavior:
   * soft lift
   * fade in
   * slight sharpen or blur reduction
________________


14.5 Transition Motion
Used for:
   * Map → Calendar
   * Calendar → Event
   * Upload step progression
   * Saved → Event
Behavior:
   * preserve directional logic
   * maintain user orientation
   * avoid visual resets when possible
________________


14.6 Confirm Motion
Used for:
   * save action
   * upload completion
   * successful edit
   * boost applied
Behavior:
   * brief
   * crisp
   * localized
Examples:
   * button state pulse
   * icon fill
   * small glow confirmation
________________


14.7 Recede Motion
Used when background loses priority.
Examples:
   * map blurs behind event detail
   * bottom nav fades when time tray expands
   * calendar dims when detail opens
Behavior:
   * dim
   * blur
   * slight scale reduction if appropriate
________________


14.8 Guide Motion
Used to:
   * indicate draggable surfaces
   * show expansion path
   * establish source-to-destination relation
Example:
   * tapped pin subtly links to detail modal rise
   * selected card expands into full detail chamber
________________


14.9 Mode Transition Logic
Map → Calendar
   * calendar rises or slides in as a controlled takeover
   * map remains faintly visible or fully replaced depending on chosen style
   * bottom nav recedes
________________


Calendar → Event
   * selected tile expands
   * surrounding tiles dim
   * detail chamber sharpens into focus
________________


Map → Event
   * selected signal enlarges slightly
   * event chamber emerges from its spatial source
   * map recedes into blur/dim
________________


Upload Step Progression
   * linear horizontal or fade progression
   * progress indicator updates clearly
   * no hard page switch feeling
________________


14.10 Micro-Interactions
Important micro-interactions include:
   * signal pin hover/tap response
   * save icon fill
   * filter chip selection
   * time pill expansion
   * inline edit entry
   * field corrected confirmation
These must remain subtle and responsive.
________________


14.11 Duration Principles
Durations should feel:
   * fast enough to avoid drag
   * long enough to communicate meaning
Guideline:
   * micro interactions = short
   * mode changes = medium
   * confirmation = brief
Avoid sluggishness.
________________


14.12 Easing Principles
Use easing that feels:
   * smooth at start
   * controlled at finish
   * non-elastic
Avoid exaggerated spring behaviors unless extremely restrained.
________________

Every motion must clarify state. If it does not clarify state, remove it.

19. Performance & Constraints
19.1 Purpose
Performance is not a technical afterthought.
In WeUP, performance directly affects:
   * trust
   * perceived product quality
   * emotional tone
   * usability under nightlife conditions
A slow nightlife radar stops feeling alive.
________________


19.2 Primary Performance Targets
Phase 0 should optimize for:
   * fast first render
   * stable map interaction
   * responsive modal transitions
   * lightweight event previews
   * acceptable OCR turnaround
   * controlled memory usage on mobile devices
________________


19.3 Critical Interaction Budgets
The following interactions must feel immediate or near-immediate:
High-Priority UI Response Targets
   * map pan / zoom responsiveness
   * signal tap response
   * event peek card appearance
   * event save feedback
   * bottom nav mode switching
These actions must never feel blocked by:
   * heavy image rendering
   * oversized overlays
   * synchronous parsing tasks
   * unnecessary re-fetching
________________


19.4 Query Budgeting
All data fetches must be scoped to the active UX need.
Map Mode
Only fetch:
   * visible map area
   * current time range
   * lightweight event payloads
Calendar Mode
Only fetch:
   * selected date range
   * display-ready card data
Event Detail
Fetch:
   * full event payload on demand
   * only when entering detail mode
________________


19.5 Partial Rendering Strategy
The UI should not wait for complete payload enrichment when not required.
Recommended approach:
Stage 1
   * render map surface
   * render lightweight signals
Stage 2
   * enrich metadata
   * load flyer thumbnails
   * populate detail data
This preserves velocity.
________________


19.6 Image Constraints
Flyers are one of the biggest performance risks.
Requirements:
   * compress on upload
   * generate thumbnail variants
   * lazy-load large images
   * crop predictably for cards
   * load full resolution only in detail mode if needed
________________


19.7 Motion Performance Limits
Motion must never compromise interaction.
Avoid:
   * too many simultaneous blur layers
   * multiple glow animations at scale
   * full-screen repaints triggered by minor actions
   * stacked animated panels
Recommended:
   * use transform and opacity-based transitions
   * reserve blur for focused modal states only
   * minimize persistent animation loops
________________


19.8 Map Load Strategy
Map performance must be protected above all else.
Requirements:
   * cluster aggressively at density
   * debounce rapid query updates
   * keep signal rendering efficient
   * limit overlay complexity while panning
   * avoid rendering unnecessary labels during active movement
________________


19.9 Upload / OCR Performance Model
Upload flow must separate:
   * client responsiveness
   * backend extraction work
UX expectations:
   * upload starts immediately
   * user sees visible progress
   * OCR/parsing status updates clearly
   * user can recover from delay without confusion
________________


19.10 Internal Scroll Constraints
Internal scroll is permitted only inside:
   * calendar board content region
   * event detail content body
   * upload step content where necessary
   * profile/saved content region if needed
The shell itself must not scroll.
________________


19.11 Offline / Weak Network Considerations
Phase 0 should tolerate poor mobile conditions.
Recommended support:
   * stale cached events for recent sessions
   * graceful empty states
   * upload retry support
   * skeleton loading instead of blank surfaces
________________


19.12 Battery / Device Constraints
Because this is a mobile-first nightlife product:
   * constant animations must be limited
   * GPS or geolocation should be used carefully
   * maps should avoid wasteful redraw cycles
   * dark mode must remain efficient, not just aesthetic
________________


19.13 Performance Integrity Rule
The app must always feel lighter than its visual richness suggests.
________________
