Documentation Matrix for Every WeUP Release (v1.0 → v1.24)
Below is a ready‑to‑use checklist that tells you what documents must exist, be versioned and be updated for each published version.
The list is grouped by release‑type (core, feature‑specific, cross‑cutting) and mapped to the phase‑based version blocks that appear in the 12‑month roadmap (Phase 0 → Phase 0.15 → Phase 0.20 → Phase 0.25 → Phase 0.30+ → Phase 1.0).
Key conventions
All docs live in the same Git‑tracked docs/ folder (or a dedicated Confluence space) and are version‑tagged (e.g. v1.07‑API‑Spec.pdf).
 Each document carries a header block with:  Version, Authors, Last‑Updated, Review‑Status.
 When a release introduces a new feature, add a new document (or a new section) and increment the version number of the parent doc.

5. Quick‑Start Template for a New Release (e.g., v1.18)
1. Create PR “Release‑v1.18‑Docs”

   * Duplicate CHANGELOG.md entry.
   * Add a new section in Release_Notes_v1.18.md.
   * Update API_v1.18.yaml (add any new endpoints).
   * Increment version in Architecture_Decision_Records/ADR-XX.md if relevant.
   2. Feature‑Spec Update

      * For each new feature, add a markdown file under features/ (e.g., features/venue_console_v1.18.md).
      * Include user stories, acceptance criteria, UI mock‑ups, and a link to the relevant ADR.
      3. Data‑Model Change

         * Modify db/schema_v1.18.sql (or EF Core migration file).
         * Update Data_Model_v1.18.md with new tables / columns and migration steps.
         4. Security Review

            * Run the Security & Compliance Checklist – note any new controls (e.g., “Add rate‑limit to video‑upload endpoint”).
            5. Test‑Plan Refresh

               * Add/modify unit & integration test cases in tests/ folder.
               * Update Test_Plan_v1.18.md with new test matrix rows.
               6. Ops Run‑Book

                  * Add deployment steps for any new background worker (e.g., “Start video‑processing worker service”).
                  7. User Docs & Marketing

                     * Write a short “How‑to” article for each public‑facing change.
                     * Prepare a one‑page “What’s New in v1.18” slide deck for internal launch.
                     8. Final Review & Sign‑off

                        * Peer‑review all changed docs.
                        * Product‑Owner signs the PR, then it is merged before the CI/CD pipeline tags the release.

	Minimum Docs (per version)

	Architecture
	ADR, System Diagram, Data Model, API Spec (C‑07‑C‑09)
	Security

	Test Plan, QA Sign‑off (C‑11)
	Delivery

	Run‑Book, Monitoring/Telemetry Plan (C‑13, C‑22)
	User‑Facing
	Help Center articles, FAQ (C‑15)
	Marketing
	Blog/Press kit, FAQ for external audience (C‑16)
	Feature‑Specific
	Media‑Ingestion Spec (M‑xx), Trust‑Graph Spec (T‑xx), Revenue‑Ops Spec (O‑xx), Intelligence Spec (I‑xx) – only when the phase introduces those capabilities
	Follow the table above, keep the docs version‑controlled, and you’ll have a complete, auditable, and searchable knowledge base for every WeUP release from v1.0 through the Phase 1 launch (v1.24).
